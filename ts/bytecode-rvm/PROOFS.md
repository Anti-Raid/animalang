# Correctness of lifting and liveness

> **Disclaimer:** these proofs were generated by Claude Opus 5.5 (Anthropic) and have not been independently verified.
> They are informal, written by hand rather than machine-checked, and describe the code as of when they were written; later
> changes to `lift.ts`, `analysis.ts` or `aot/liveness.ts` may invalidate them.

This file proves that four compiler steps preserve the meaning of a program:

1. `blockEscapes` (`lift.ts`): an early-exit `%call/ec` or `%call/cc` becomes a `%block`.
2. `splitCaseLambdas` (`lift.ts`): a local multi-clause `%lambda` becomes one binding per clause.
3. `liftIn` (`lift.ts`): lambda lifting of `%letrec` lambdas.
4. Liveness:
   - `CallLiveness` (`analysis.ts`) decides which assigned variables need a box;
   - `Liveness` (`aot/liveness.ts`) decides what resume code loads and spills.

Each section states the conditions the code checks, then shows that under them the transformed program behaves exactly like the original. "Behaves like" means the same values, effects, errors and termination. Procedure names in tracebacks may differ.

## 0. Model and assumptions

**Source semantics.** Programs are core forms (`%lambda`, `%let`, `%let*`, `%letrec`, `%let-values`, `%set!`, `%if`, `%block`/`%escape`, `%loop`, `%with-mark`, `%catch`, calls, intrinsic calls).

They mean what a store-based machine gives them:

- Every evaluation of a binder allocates a fresh **location** for each name it binds. A variable reference reads its location, and `%set!` writes it.
- A closure pairs code with the environment (name to location) where it was made.
- A continuation is an immutable control context together with the dynamic-wind list and the marks. Invoking it replaces the current context. The store is never restored.

**Assumptions.**

- **A1: no shadowing of core forms or intrinsics.** The compiler rejects binding their names, so a symbol in operator position that names a form or intrinsic always means that form.
- **A2: `assigned` is conservative.** `assignedNames` collects every symbol that appears as a `%set!` target anywhere in the program. If a binding is ever assigned, its name is in the set. Names are compared by symbol, so the set can only be too large.
- **A3: `%letrec` evaluation order,** as `#compileLetrec` compiles it:
  1. all lambda inits are made first; making a closure runs no code and cannot fail;
  2. their names are then set;
  3. the other ("value") inits run in order, and each name is set after its init.
- **A4: `%escape` stays in one function.** An `%escape` only targets a `%block` of the same function. `#compileEscape` rejects anything else (`Msg.EscapeFromLambda`).
- **A5: a value init's continuation runs once.** The continuation of a `%letrec` value init is not invoked again after that init has returned. R6RS requires this (11.4.6), and without it a value's binding is effectively assigned. Only §3 relies on A5. §4 does not: it holds without A5, see 4.3.
- **A6: interrupt checks are not calls.** The `(%interrupt)` checks the compiler adds (see Interrupts in the README) are added after lifting and the core forms' liveness analysis, which never see one; AOT liveness, which works on the bytecode, sees each as the host call it is. A check calls no procedure and captures no continuation: its handler can only continue, pause the running coroutine (which then resumes once, where it was) or stop the evaluation for good. So adding them changes nothing proved here.

**Notation.**

- *Within*: `within(L)` is the list of inits and body forms of a `%letrec` `L`, the only places its names are in scope.
- *Free locals*: `FV(e)` is the set of free local names of `e`, as `freeIn` computes it over expression positions. `%set!` targets and block labels are not expression positions.
- *Call site*: a node `(f a1 … am)` with `f` in operator position.

## 1. `blockEscapes`

**Rewrite.** For `E = (C (%lambda (k) B1 … Bn))` with `C ∈ {%call/ec, %call/cc}`:

```
E  ⟶  (%block L B1' … Bn')
```

Here `L` is fresh, and each call `(k a…)` in the `Bi` becomes `(%escape L v)`, where `v` is `a` if there is one argument and `(%values a…)` otherwise.

**Conditions checked.**

- (C1) `k` is not in `assigned`.
- (C2) Every free occurrence of `k` in the `Bi` is the operator of a call that is not inside any `%lambda` (`onlyCalled`).

**Lemma 1.1 (the call site's context).** Fix one evaluation of `E` with continuation `κ`. While code of the `Bi` that is not under a `%lambda` runs in the body activation `A` this evaluation created:

- the control context is `K ∘ κ` for some `K`;
- the dynamic-wind list and the handler/mark state equal those at entry to `E`, apart from `%with-mark` regions opened by that code itself.

*Proof.* Code of the `Bi` outside any lambda is evaluated only as part of evaluating the body in `A`. A continuation captured at such a point has the form `K ∘ κ`, and so does its re-entry. The context above `E` is immutable, so `κ` is the same in every such timeline. Dynamic-wind changes the wind list only while its thunk runs, and the thunk is a lambda, so by (C2) no call site sits in it. A re-entry restores the wind list of the capture point, which is again `E`'s. □

**Theorem 1.** `E ≡ (%block L B1' … Bn')`.

*Proof.* We match the two programs step by step. They agree until a call site `s = (k a…)` in `A` runs.

- **Original:** `k` is `κ` (by C1 it stays bound to `κ`), so the values `v̄` are delivered to `κ`.
- **Rewritten:** `(%escape L v)` delivers `v̄` to the continuation of the block, which is `κ` because the block is evaluated in `E`'s place. `%escape` also restores the marks to the block's depth (`MarkRestore`).

By Lemma 1.1:

- no dynamic-wind after-thunk is pending between `s` and `κ`, so invoking `κ` would run none;
- the marks invoking `κ` would restore are those the `MarkRestore` restores;
- both run in the same coroutine, so `Msg.ContinuationBoundary` cannot arise in the original.

Zero or several arguments become `(%values …)`, which is exactly what `κ` receives. By C2, `k` is never used any other way, so its identity is never observed. Finally, `E`'s body is in tail position exactly when `E` is, and the block's body inherits `E`'s tail position (`isTail: target.isTail`). □

## 2. `splitCaseLambdas`

**Rewrite.** Take a binding `x = (%lambda c1 … cn)` with `n ≥ 2` in a `%let`, `%let*` or `%letrec`, with `x ∉ assigned`.

- Each clause becomes a one-clause `%lambda` bound to a fresh name `xi` in a `%letrec`. That `%letrec` is placed where the clause expressions are evaluated in the same environment as before:
  - in place, for a `%letrec`;
  - around the `%let`, for a `%let`;
  - after the preceding bindings, for a `%let*`.
- Each call `(x a1 … am)` in scope (`usesOf` over `within`) for which some clause accepts `m` gets operator `xi`, where `i` is the first clause with `accepts(ci, m)`.
- `x` stays bound to `(%make-case-lambda x1 … xn)` if any other use remains.

**Lemma 2.1 (`accepts` matches `CaseLambda.select`).** `accepts(c, m)` holds exactly when `min ≤ m ≤ max` for the clause's `closureArity`.

*Proof.*

- Padded: `min = 0`, `max = ∞`, and `accepts` is true.
- With a rest parameter: `min = params`, `max = ∞`, and `accepts` means `m ≥ params`.
- Otherwise: `min = max = params`, and `accepts` means `m = params`. □

**Theorem 2.** The rewrite preserves meaning.

*Proof.*

1. **Evaluation.** Closure creation has no effects and cannot fail. So making the clause closures earlier, all at once, is unobservable. Each evaluation of the form still makes exactly one procedure for `x` when `x` is kept, so `eq?` on `x` behaves the same.
2. **Scope.** The clause bodies see the same environment as before:
   - the fresh names cannot capture anything;
   - for a `%let`, the inits were evaluated outside its scope, and the new `%letrec` binds only fresh names;
   - for a `%let*`, the clauses sit after exactly the bindings before `x`.
3. **Calls.** A rewritten call site refers to this binding of `x` (`usesOf` skips positions where `x` is shadowed). Since `x ∉ assigned`, its value there is the procedure `P` made from `c1 … cn`. Calling `P` with `m` arguments runs `select(m)`, which by Lemma 2.1 is clause `i`, the same closure `xi` names. The argument count is static because the site is a plain call; `%apply` goes through the kept procedure.
4. **The rest.** Uses that are not calls, or calls no clause accepts, still use `x`, which is still `P`. Calls with no fitting clause therefore still raise `Msg.NoClause`. □

## 3. Lambda lifting (`liftIn`)

**Rewrite.** For a `%letrec` `L` with bindings `fj = λj`, `liftIn` computes a set `Lifted` of names and, for each `f ∈ Lifted`, a list `V(f)` of free locals. Then:

- `f`'s lambda gets fresh parameters `v'` for each `v ∈ V(f)`, placed before its own parameters. Every unshadowed free `v` in its body becomes `v'`.
- Every call site of `f` gets `V(f)` as extra leading arguments:
  - inside a lifted lambda `h`, those arguments are `h`'s own fresh parameters;
  - elsewhere, they are the names themselves.

**Conditions** (the fixpoint in `liftIn` and `walk`). For every `f ∈ Lifted`:

- **(L1)** `f`'s init is a one-clause `%lambda`, and `f ∉ assigned`.
- **(L2)** Every free occurrence of `f` in `within(L)` is the operator of a call whose argument count the clause accepts (`uses.other` is false and `accepts` holds).
- **(L3)** `V(f) = FV(body of f) ∩ scope`, closed under `g ∈ V(f) ∧ g ∈ Lifted ⇒ V(g) ⊆ V(f)`. Here `scope` holds the locals bound around `L` plus `L`'s names.
- **(L4)** No `v ∈ V(f)` is in `assigned` or in `unsafe`.
- **(L5)** For every call site `s` of `f` not inside a lifted lambda, no `v ∈ V(f)` is bound between `L` and `s` (`c.bound ∩ V(f) = ∅`).

`unsafe` is built in `walk`. It holds the value names of enclosing `%letrec`s whose inits may not have run when code at this point runs:

- a value init and everything inside it sees the values of its own `%letrec` as unsafe;
- if any value init of a `%letrec` mentions one of its lambdas (`runsEarly`), its lambdas and body see them as unsafe too.

The loop only ever removes names, so it terminates. Its result satisfies L1–L5 simultaneously: the loop exits only when a pass removes nothing, and `calls` and `fv` are computed in that last pass with `skip = Lifted`.

**Lemma 3.1 (every use is a call).** In the original program, every reference to the binding `f` evaluates `f` as the operator of a call with an accepted count.

*Proof.* The scope of `L`'s names is exactly `within(L)`, and L2 covers every unshadowed occurrence there. □

**Lemma 3.2 (the extra arguments name the right bindings).** Let `s` be a call site of `f` and `v ∈ V(f)`. The expression passed for `v` at `s` evaluates to the location that `v` denotes in the environment where `f`'s closure was made, in the same activation.

*Proof.* Case on where `s` is.

- **`s` is not in a lifted lambda.**
  - `s` refers to the binding `f` of `L`, so its environment extends the activation `A` of `L` in which that `f` closure was made. The closure's own environment is `A` as well.
  - `v ∈ scope` is visible in `A`, and by L5 nothing between `L` and `s` rebinds it. So `v` at `s` is `v` in `A`.
- **`s` is in a lifted lambda `h`.**
  - Since `s` uses `f` unshadowed, `f ∈ FV(h) ∩ scope ⊆ V(h)`, and by L3, `V(f) ⊆ V(h)`. So the renaming map `rewrite` uses inside `h` contains `v`, and the argument is `h`'s fresh parameter `v'`.
  - The fresh parameter cannot be shadowed. By induction on the call chain (each call to `h` meets this lemma), `v'` holds the location, or under L4 the value, of `v` in `A`. □

**Lemma 3.3 (the value is ready and fixed).** Whenever a call site of `f` runs, every `v ∈ V(f)` holds its one and only value.

*Proof.* By L4, `v ∉ assigned`, so no `%set!` changes it; with A5, nothing else rebinds it. It remains to show `v` is initialized. Case on what `v` is.

- **A parameter, or a `%let`, `%let*` or `%let-values` variable:** initialized when bound.
- **A lambda name of any enclosing `%letrec`:** set before any code of that `%letrec` runs (A3).
- **A value name of `L` itself.** It is not unsafe, so `runsEarly` is false: no value init of `L` mentions a lambda of `L`.
  - Only the inits and body of `L` can name `f` or the other lambdas of `L`.
  - While the value inits run, none of them names a lambda of `L`, and the lambdas' closures are reachable only through those names.
  - So no call to `f` runs before the body, and by then every value is set.
  - A continuation invoked from a value init resumes an activation of `L` whose values were already set.
- **A value name of an enclosing `%letrec` `L'`.** It is excluded unless `L` sits in `L'`'s lambdas or body with `runsEarly(L')` false. Then the same argument applies to `L'`. □

**Theorem 3.** Lifting preserves meaning.

*Proof.* We relate the two programs' states with a simulation relation `≈`. It is the identity except in two places:

1. Where the original has a closure of `f` made in activation `A`, the lifted program has the constant closure `f'`.
2. Inside a call of `f'`, each parameter `v'` is bound to the value of `v` in `A`.

We check that every step preserves `≈`:

- **Making `f`.** Only the captured free locals differ. For `v ∈ V(f)` the closure no longer captures `v`, and `f'` reads its parameter instead.
- **Calling `f`.** Every use of `f` is a call (Lemma 3.1). Both programs:
  - evaluate the same operands, in the same order;
  - then the lifted one evaluates the extra arguments, which are variable references with no effects that cannot fail (Lemma 3.3);
  - bind the same parameters, because the extra ones come first and the count is accepted (L2). For a padded clause or a rest parameter, the prepended parameters leave the original arguments aligned.

  In the body, each rewritten `v'` reads the value the original's `v` would read (Lemmas 3.2 and 3.3). Nothing else in the body is renamed: `rewrite` skips names that are bound inside it.
- **Calls from `f'` to another lifted `g`.** The operator `g` has become `g'`, a parameter holding the value of `g`, and `g ∈ V(f)` by L3. The extra arguments are mapped through `f'`'s renaming, since `V(g) ⊆ V(f)`. That is the same situation as a call of `g`, so Lemmas 3.2 and 3.3 apply.
- **Identity.** A lifted lambda is only ever passed on as an extra argument and called. So using one closure where the original made one per activation is not observable.

Every step preserves `≈`, and `≈` preserves values, effects, errors and termination. □

**Remark.** Correctness does not need `f'` to be free of captures; that is only the optimization's goal. A free local that `f` only assigns is not in `FV(f)`. It is also in `assigned`, so it cannot be in any `V`. `f'` then still captures it where it stands, which is correct but misses the optimization.

## 4. Liveness

### 4.1 What the VM does differently from locations

The VM keeps a variable either in a **register** of its function's frame, or in a **box** (a heap cell) whose reference sits in a register. A closure copies the registers it captures when it is made (`NewClosure`).

Only three things can make a register and the location it stands for disagree:

- **(D1) Closure copies.** A captured variable that is assigned needs a box. That is `isCaptured`, part of `VariableMetadata.isBoxed`.
- **(D2) Continuation re-entry.** A frame captured by `%call/cc` or `%call/comp` is shared. Re-entering it runs a copy (`Frame.thaw`, `#compose`) whose registers are those at the capture point. A later assignment to an unboxed variable is lost in that copy.
- **(D3) Nothing else.**
  - Escapes, `%catch` and returns resume the frame object itself, at its pending call.
  - A coroutine resumes its one suspended frame.
  - Rebuilding direct code into heap frames copies the registers into a frame that replaces the abandoned direct activation.

  None of these leaves two live copies that can each be written.

A capture point is always a pending **non-leaf call** of the frame, because leaf intrinsics never call back into the VM. For frames further out, it is their own pending call, which is also a call.

### 4.2 `CallLiveness` (which variables get a box)

`CallLiveness.expr(e, out)` returns `live(e, out)`: the variables that are assigned and not captured, and that may be read after entering `e` before being assigned again, given `out` after `e`. At each non-leaf call it marks `liveAcrossCall` on every variable in `out` after the call.

**Lemma 4.1 (soundness).** For every form, `live(e, out)` contains every tracked variable with a path from entry to `e` that reads it before assigning it. The paths are those of the order `#compile` evaluates `e` in, continuing with any variable of `out` read later. At each non-leaf call, the marked set contains every tracked variable read after the call before being assigned.

*Proof.* By structural induction, one case per form, checking that each case follows the compiled order.

- **Symbols** add their variable. **`%set!`** evaluates its value first, then removes its variable.
- **Calls:** the operator, then the operands, left to right, then the call (`#compileNormalCall`). They are processed in reverse from `out`, and `out` is marked when the call is not a leaf. An intrinsic's operator is not an expression.
- **`%if`:** each test before its branch; the chain of tests joins with union.
- **`%let`, `%let-values`:** inits in the outer scope, in order; bind; body. **`%let*`:** each init in the scope of the bindings before it.
- **`%letrec`:** by A3, the lambda inits run nothing and are set before any value init. So a lambda name is live back to the start of the `%letrec`, and each value name back to its own init.
  - The analysis now skips lambda inits in its per-init loop and removes every name at the start.
  - Before this sweep it removed a lambda name at the lambda's own position. A read of that name in a later init was then not live across a call in an earlier init. See 4.3.
- **`%block`/`%escape`:** an `%escape` continues from what is live after its block (the `blocks` map). By A4 escapes never cross a lambda, and each lambda is analysed on its own with an empty map.
- **`%loop`:** the body's end flows back to its start. The loop iterates `head ← head ∪ live(body, head)` from ∅, or from the result of an earlier pass. Everything is monotone and every earlier result lies below the new least fixpoint, so the loop reaches the least fixpoint.
- **`%catch thunk handler [pre]`:** thunk, then pre, then the call; then, only after an error, the handler expression and its call. `after = out ∪ live(handler, out)` covers both ways out of the call, and all of `after` is marked.
- **`%with-mark`:** key, value, then body, with no call among them.
- **`%lambda`:** it runs nothing where it stands; its captured variables are boxed by D1. □

**Theorem 4.** An assigned, uncaptured variable `x` without a box (`liveAcrossCall(x)` false) behaves exactly like a location.

*Proof.*

1. By D1–D3, the register of `x` in a frame can only differ from the location in a copy made by re-entering a continuation captured at a non-leaf call `c` of that frame.
2. In that copy, execution resumes right after `c`, with `x`'s register as it was at `c`.
3. If that stale value were ever read, there would be a path from right after `c` to a read of `x` with no assignment of `x` in between. Then `x ∈ out(c)`, and Lemma 4.1 would have marked it at `c`, which contradicts the hypothesis.
4. So on every path the copy takes, `x` is assigned before it is read, and the stale value is never observed. □

### 4.3 The `%letrec` bug the proof found

This program re-enters an init with the second init's value already assigned:

```
(letrec ((a (call/cc (lambda (c) (set! g c) 1))) (f (lambda () 1)) (b f))
  (set! r (cons (procedure? b) r)) (set! f 5) (when (< (length r) 2) (g 2)) r)
```

- **Semantics:** `f` is a location holding `5` on the second pass, so the result is `(#f #t)`.
- **Old analysis:** it placed `f`'s definition after `a`'s init, so `f` was not live across the `call/cc` and was not boxed. The re-entered copy read the stale lambda and gave `(#t #t)`.
- **Now:** the fix makes Lemma 4.1's `%letrec` case exact, and the test "boxes a letrec lambda name assigned after a call in an earlier init" covers it.

The program invokes an init's continuation again, which A5 forbids. That is why §4 does not assume A5: boxing must be right even then.

### 4.4 `Liveness` (what resume code loads and spills)

Resume code (`ResumeEmitter`) keeps registers in JS locals `ri`.

- **At entry,** it loads `ri = regs[i]` for `i ∈ entryLive`. That set is `liveIn(0)` together with `liveIn(R)` for every resume point `R`, where a resume point is the `resume` of a `Call` or of a `HostCall` not in tail position.
- **Before leaving at a resume point `R`,** it writes back `spillsFor(R) = liveIn(R) ∩ written`, plus the argument window when it is read from `regs`.
- **On an exception,** it writes back everything in `written`.

**Soundness conditions of the dataflow.**

- **(S1) Successors.**
  - Every successor ip is a block start. `basicBlockStarts` adds every ip operand, including the targets of `ELSE` and `JUMP`, and the ip after every instruction that splits: `IF`, `ELSEIF`, `BLOCK`, `LOOP`, `ENDLOOP`, `JUMP`, and a non-tail `CALL` or `CALLHOST`.
  - `ENDIF` does not split, but its successor, the next ip, is always a start: `#compileIfCall` puts the chain's end label right after it, and at least one `ELSE` jumps there.
  - `RETURN` has no successor. Anything after it that is reachable is the target of a jump, and so a start.
  - A block without a terminator falls through to the next start (`{ k: "Jump", target: ip }`).
  - Each terminator lists every place control can go next:
    - `Branch`: both ways;
    - `Block`/`Loop`: their body;
    - the block's end: reached through the escapes and falling-through jumps that target it;
    - a non-tail call: its resume;
    - a self tail call: 0.
- **(S2) Uses.** `#instUses` and `#termUses` list every register an instruction reads:
  - an intrinsic reads only its window `[start, start + nargs)`;
  - `NewClosure` reads the local registers it captures;
  - `MarkRestore` reads `reg` and `reg + 1`;
  - `SetBox` reads the box register and the value.
- **(S3) Definitions.** `#instDefs` lists only registers an instruction always writes when it completes: its `dst`, the window of an `Unpack`, and `reg`/`reg + 1` of a `MarkSave`. It excludes `SetBox`, which writes into a box rather than the register.

**Lemma 4.2.** By S1–S3, the least fixpoint `#compute` reaches is a sound over-approximation: `liveIn(b)` contains every register that some path from `b` reads before writing. This is the standard result for monotone backward dataflow over a finite lattice. The loop starts from ∅, and the transfer `live = uses ∪ (live − defs)` is monotone.

The self tail call (`MaybeSelfTailCall`) writes the parameters and then jumps to 0. The analysis does not remove the parameters there. That only makes the result larger, which is still sound.

**Theorem 5.** Whenever resume code reads the local `ri`, it holds the register's value as the machine defines it.

*Proof.* We prove two invariants, each by induction over executions.

- **I1 (entry).** A resume function starts at some `R ∈ {0} ∪ resume points` (`frame.ip`).
  - Any register a path from `R` reads before writing is in `liveIn(R) ⊆ entryLive` (Lemma 4.2), so it is loaded.
  - Registers not loaded are written before they are read.
- **I2 (exit).** When the function leaves at resume point `R`, `regs[i] = ri` for every `i ∈ liveIn(R)`.
  - If `i ∈ written`, the spill writes it.
  - If not, `ri` was loaded from `regs[i]` at entry and never changed. Nothing else writes `regs` while this function runs: the executor writes a frame's registers only when binding a new frame, when a tail call resets it, or through copies.

Every later entry at `R` reads `regs` in the state I2 guarantees. That is true whether it is the same frame resumed, or a copy made by re-entering a continuation, which copies `regs` as they were at `R`.

Other exits do not resume this activation at an arbitrary ip:

- A return or tail call never resumes it.
- An exception spills `written` and raises without continuing: host errors are never continuable, and a catch token resumes only a frame whose `escape` is set, meaning one waiting in its pending call at a resume point.
- A tail call's `frame.ip = term.ip` is used only for error positions, for the same reason.

Direct code never resumes in the middle of a function. When it suspends, it rebuilds a frame at `rip`, which is a resume point, with every register (`allRegs`), so I1 holds there too. □
